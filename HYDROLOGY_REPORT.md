# Terra Hydrology Architecture Investigation

Code facts below describe the current checked-in workspace as inspected on 2026-11-09. File references are repository-relative and include source line numbers. The sections marked **Assessment** contain analysis or suggestions rather than implemented behavior. No code was changed and no tests, benchmarks, or profiling were run.

## 1. Executive architecture summary

Terra currently has a 283 × 212 tile world by default, with normalized procedural elevation and five terrain visuals. World cells hold immutable elevation and a one-time terrain classification. There is no drainage graph, river/lake state, terrain water-body state, or hydrological routing. See [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:10), [`Terrain.kt`](src/commonMain/kotlin/terra/world/Terrain.kt:3), and [`GameConfig.kt`](src/commonMain/kotlin/terra/GameConfig.kt:3).

Weather already calculates actual precipitation in millimeters, adds land rain to a soil store, subtracts land evaporation, and removes drainage above a field-capacity threshold. But drainage is a local scalar discarded inside the update; it is neither exposed nor transferred to another tile or surface-water store. Rain above the 250 mm soil-capacity clamp is also discarded. Thus hydrology has a viable physical input but needs a new, explicit runoff/drainage output or accounting path. See [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:193) and constants at lines 505–510.

The renderer uses a 64 × 64 atlas tile for each base terrain type, scaled to one map-coordinate unit per tile, plus one-pixel-per-tile bitmap overlays. This gives a compatible place to draw dynamic river masks and water-level tints without multiplying base terrain types. Existing overlays are weather diagnostic layers; no water-surface overlay or neighbor-aware terrain connection system exists. See [`TerrainMapView.kt`](src/commonMain/kotlin/terra/render/TerrainMapView.kt:22).

**Assessment:** A lightweight hydrology can precompute a drainage topology from elevation and ocean outlets, then update per-tile water inputs/discharge on a slower simulated-time cadence using actual precipitation and the drainage amount already calculated by weather. A stored flow graph, not per-frame water motion, fits the current architecture. Closed depressions and flats mean a raw “choose lowest neighbor” rule is not guaranteed to drain or remain acyclic; depression/spill routing or explicit lake sinks should be considered before relying on it. This is a design consideration, not implemented functionality.

## 2. Current elevation and geographic representation

### World and coordinates

- Defaults are `MAP_WIDTH_TILES = 283`, `MAP_HEIGHT_TILES = 212`; `World` accepts alternate positive or invalid dimensions without explicit validation. Linear indexing is row-major `y * width + x`; `World.get(x, y)` directly indexes the backing array and does not clamp or wrap coordinates. [`GameConfig.kt`](src/commonMain/kotlin/terra/GameConfig.kt:3), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:10), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:20), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:109)
- Tile size in world-map coordinates is 1 × 1. Artwork is 64 × 64 pixels and the terrain tile container is scaled by 1/64 in both axes. The initial screen zoom is calculated from the 1440 × 960 window and map dimensions; panning and zooming are view transforms, not world geometry. [`TerrainMapView.kt`](src/commonMain/kotlin/terra/render/TerrainMapView.kt:43), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:54), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:290)
- The world is not explicitly marked as wrapping. Weather advection wraps horizontally and clamps vertically, while world lookup, terrain rendering, selection, and map edges are bounded. This means weather's horizontal periodicity is not shared by the physical world representation. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:295), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:488), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:20)

### Elevation creation and storage

- `World.generate()` creates a temporary elevation `DoubleArray(width * height)`, temperature array, and moisture array, then copies their values into `Cell` objects. Elevation is a normalized scalar clamped to `[0.0, 1.0]`, calculated from base elevation plus continental, regional, and detail FBM noise weighted by settings. It is not a physical height in meters; the UI displays `elevation * 100` as a percentage. [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:26), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:42), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:50), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:188)
- Defaults: base 0.29; continental scale/octaves/strength 85/4/0.56; regional 13/4/0.08; detail 6/3/0.02; persistence 0.5; lacunarity 2.0; sea level 0.305; mountain threshold 0.6. Clamping can create equal values at 0 or 1 where noise exceeds the range. [`Terrain.kt`](src/commonMain/kotlin/terra/world/Terrain.kt:18)
- `Cell` is a data class whose fields are `val`; elevation and terrain cannot be changed through a returned cell. The backing cell array is private, and `World` exposes only a getter. There is no erosion, sediment, terrain mutation, or run-time elevation setter. Regenerating settings constructs a new whole `World`, rather than mutating elevations. [`Terrain.kt`](src/commonMain/kotlin/terra/world/Terrain.kt:11), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:17), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:152)
- The generator uses three scales of simplex-derived FBM. It does not deliberately create river valleys, guarantee periodic noise across X, enforce a continental edge, or preprocess sinks. Depressions, near-flats, plateaus from clamping, and disconnected inland land basins are all possible; their frequency or connectivity has not been measured in this read-only inspection. Ocean tiles are every cell whose elevation is strictly below sea level. [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:45), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:89)

### Geographic and water-body representation

- `Terrain.OCEAN` is a classification, not a separate dynamic water body. There are no coast, lake, river, river-mouth, wetland, slope, flow-direction, catchment, or basin types. [`Terrain.kt`](src/commonMain/kotlin/terra/world/Terrain.kt:3)
- There is no special coastline or island algorithm: coastlines and islands emerge solely from the sea-level threshold over generated elevation. Ocean-connected basins are not explicitly labelled; a tile below sea level is ocean regardless of neighborhood connectivity.
- Determinism: the `World` seed initializes `Random(seed).nextInt()` as a salt; noise then uses deterministic integer lattice hashing with octave offsets. The weather regional vortex initialization also uses `Random(world.seed xor constant)`. The world seed is currently initialized to `31742` in `AtlasScene`. For the same runtime/platform and settings this is designed to be repeatable; the source does not specify cross-version/platform bit-for-bit guarantees. [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:16), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:164), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:407), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:30)

## 3. Current water-cycle data and conservation

### Units, arrays, and observable quantities

`WeatherSimulation` owns flat arrays of length `width * height`. Atmospheric vapor, cloud water, soil water, precipitation depths, and rain totals are represented in millimeters per tile-column (a depth), not a volume. Temperature is °C; wind is tiles/day. Arrays are private, with scalar getter methods. There is no tile-area conversion or catchment discharge volume. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:15), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:21)

| Value / accessor | Meaning and time basis |
|---|---|
| `atmosphericWaterMm`, `cloudWaterMm`, `soilWaterMm` | Current stored depth (mm) at the end of the latest weather substep. |
| `rainMmThisUpdate(x,y)` | Sum of precipitation depth (mm) over all substeps in the latest `step(seconds)` call; reset to zero at the start of that call. |
| `precipitationMmPerHour(x,y)` | Update-total rain divided by elapsed hours passed to `step`; an average rate over that outer update, not an instantaneous rate. |
| `peakSubstepPrecipitationMmPerHour(x,y)` | Maximum per-substep rate during that outer update; each substep is at most 3 simulated hours, though it can be shorter. |
| `thirtyDayRainMmPerHour(x,y)` | Exponential-response smoothed rate with a nominal 30-day response constant; it is not a literal rolling 30-day sum/mean. |
| `annualizedRainMmPerYear(x,y)` | The smoothed rate multiplied by 365 × 24 hours; a derived annualized estimate, not a year-long accumulated total. |

Definitions and calculations: [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:84), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:114), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:129), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:207), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:213), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:499)

### Where water enters, moves, and leaves

- **Initialization:** each tile starts with atmospheric vapor at 45% of the temperature-dependent saturation-column capacity. Land starts at half the 250 mm soil capacity (125 mm); ocean soil storage is zero. Clouds and rain state start at zero by JVM/Kotlin array initialization. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:59), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:72), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:505)
- **Land precipitation input:** cloud water rains out once a tile's cloud store crosses a hysteretic threshold (starts at 2 mm, stops at 0.5 mm); active rainout converts a fraction of cloud water to `rainMm` each substep. For non-ocean cells, that rain is added to soil after subtracting evaporation. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:182), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:188), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:196)
- **Ocean precipitation:** rain is removed from cloud water and counted in rain output, but does not enter soil because the soil update is skipped for `Terrain.OCEAN`. Ocean is a source for evaporation, but there is no explicit ocean surface-water state or ocean precipitation sink ledger. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:193), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:196)
- **Evaporation:** the potential rate is up to 6 mm/day multiplied by solar input, temperature warmth, available water, and elapsed-time fraction. Ocean uses available-water fraction 1 and evaporation is added directly to atmospheric vapor; this implicitly treats ocean water as an effectively unlimited external source. Land evaporation is bounded by existing soil water and is subtracted in the soil update. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:152), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:157), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:159)
- **Soil capacity and drainage:** land soil is updated as `(soil - evap + rain).coerceIn(0, 250 mm)`. Excess above field capacity (120 mm) is multiplied by `1 - exp(-elapsedDays / 5)` and removed from the soil store. The local `drainedMm` is not retained, returned, or routed; it disappears from represented water. Rain above capacity is clipped and also disappears. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:196), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:199), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:201), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:507)
- **Atmosphere:** vapor and cloud water are advected using scratch arrays and bilinear weights, which prevents deposited water from being transported twice within one pass. X wraps, Y clamps to the polar rows. Condensation moves vapor into cloud water; cloud evaporation moves it back; rainout removes cloud water into precipitation. There is no snow storage, sublimation, groundwater reservoir, or explicit global water budget. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:284), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:309), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:340), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:170)

**Conservation conclusion:** internal atmospheric transport is designed as redistribution, and land rain/evaporation alter soil and atmosphere as described. The complete represented model is not water-conserving: ocean evaporation enters from an unlimited implicit reservoir; soil drainage and over-capacity rainfall are discarded; precipitation on ocean tiles leaves cloud storage without a modeled ocean store; and there is no complete boundary/accounting ledger. A future hydrology system should consume drainage at the point where it is calculated, or expose its amount per tile and substep. It should not reconstruct runoff from humidity or cloud cover. Also decide explicitly whether any overflow is surface runoff, whether drainage is subsurface flow, and whether both feed river discharge; avoid adding the same rain a second time if using `rainMmThisUpdate` plus drainage.

## 4. Current climate and biome architecture

- World generation first assigns only physical ocean, mountain, and provisional plains terrain. After the weather-only 30-day equilibration and 180-day observation, the sampled mean air temperature and annualized precipitation classify land cover once. The old synthetic precipitation proxy and `Cell.moistureAvailability` field have been removed. [`World.kt`](src/commonMain/kotlin/terra/world/World.kt), [`ClimateBootstrap.kt`](src/commonMain/kotlin/terra/weather/ClimateBootstrap.kt), [`ClimateBiomeClassifier.kt`](src/commonMain/kotlin/terra/world/ClimateBiomeClassifier.kt)
- Runtime local precipitation drives `climateRainMmPerHour` through an exponential moving response with a 30-day time constant. `annualizedRainMmPerYear` derives from this smoothed rate. Separately, the initialization sampler integrates per-substep rain depth and mean simulated air temperature for the one-time biome assignment; no live biome reclassification follows. Temperature has diurnal solar forcing, with no axial tilt or annual seasonal cycle. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt), [`ClimateBootstrap.kt`](src/commonMain/kotlin/terra/weather/ClimateBootstrap.kt)
- Biome classification occurs once after bootstrap, not during runtime weather updates. Changing settings in the UI recreates the provisional world and weather simulation, then repeats initialization. [`World.kt`](src/commonMain/kotlin/terra/world/World.kt), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt)
- Complete `Terrain` list: `PLAINS`, `MOUNTAINS`, `WOODS`, `DESERT`, `OCEAN`, `TUNDRA`. Classification preserves ocean and high-elevation mountains, maps very cold land to Tundra, and maps other sampled aridity and temperature categories to the land-cover types. [`Terrain.kt`](src/commonMain/kotlin/terra/world/Terrain.kt:3), [`ClimateBiomeClassifier.kt`](src/commonMain/kotlin/terra/world/ClimateBiomeClassifier.kt)
- Terrain classes do not change infiltration, soil capacity, evaporation, drainage, or runoff. Weather distinguishes only `Terrain.OCEAN` from non-ocean for soil and evaporation behavior; all land tiles use the same soil capacity, field capacity, and drainage response. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:153), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:196)

**Assessment:** Riverbanks, wetlands, floodplains, lakes, and flooded states are absent. Future visual biome classification should be kept separate from physical elevation, soil parameters, and water state; current `Cell` combines immutable physical-like fields with a static terrain category but has no mutable hydrologic properties. A river overlay can cross terrain categories without adding a base biome enum entry.

## 6. Simulation timing and performance constraints

- KorGE supplies variable frame delta `dt.seconds` to the map updater. Simulation is advanced only when not paused and `dt.seconds > 0`. `weatherTickElapsedRealSeconds` accumulates real seconds; once at least 0.05 seconds has elapsed, the code calls `weather.step(pendingWeatherSimulationSeconds)` once and clears pending simulation time. It then applies modulo to tick elapsed rather than looping over missed ticks. [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:85), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:309)
- Speed multipliers: realtime 1 simulated second/sec; one hour/sec; 12 hours/sec; one day/sec; one week/sec; one 30-day month/sec. At nominal 0.05 real-second weather ticks, the month setting batches about 1.5 simulated days per call. [`SimulationSpeed.kt`](src/commonMain/kotlin/terra/simulation/SimulationSpeed.kt:3), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:90)
- `WeatherSimulation.step` divides all supplied simulated seconds into `ceil(seconds / 3 hours)` substeps (at least one), so normal substeps are bounded to three simulated hours. A large frame hitch or accumulated pending interval can still produce arbitrarily many substeps; total work scales with elapsed simulated time. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:114), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:121)
- Each weather substep runs atmospheric transport, thermal updates, air-temperature updates, then scans every tile to process evaporation, condensation, precipitation, soil updates, and climate smoothing. Atmospheric transport has scratch arrays for double-buffered accumulation. There is no hydrology scratch buffer, flow accumulation, incremental dirty-tile update, or cache beyond existing persistent arrays. [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:135), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:147), [`WeatherSimulation.kt`](src/commonMain/kotlin/terra/weather/WeatherSimulation.kt:284)
- Overlay refresh has its own 0.05 real-second accumulator, independent of weather-step call ownership, though it runs in the same UI updater. Each visible non-wind layer recolors all 283 × 212 pixels; wind clears and redraws a sparse arrow field. Weather update and overlay update cadence are therefore coupled to frame execution but can be separated for a hydrology system. [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:88), [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:97), [`TerrainMapView.kt`](src/commonMain/kotlin/terra/render/TerrainMapView.kt:95)
- Regenerating terrain settings reconstructs `World` and `WeatherSimulation`, resetting elapsed time, moisture, climate smoothing, and pending timing accumulators. [`AtlasScene.kt`](src/commonMain/kotlin/terra/ui/AtlasScene.kt:152)

**Assessment:** Precompute static routing once per world generation, then update a scalar water/discharge state at a coarser simulated-time cadence. Batch the accumulated rain/drainage over elapsed time and process stored flow topologically or through a bounded number of catchment steps; do not tie the network to the 20 Hz render overlay refresh. At month speed, weather itself already performs multiple 3-hour substeps per nominal UI tick, so adding a per-tile hydrology pass on every weather substep would multiply full-grid work. No benchmark was performed.

## 7. Drainage-network feasibility and geographic edge cases

### Verified geography constraints

- Elevation is a clamped multi-scale noise field with no sink filling, flat resolution, flow direction, or outlet calculation. Ocean is assigned by the sea-level threshold, whether or not a path from a land tile reaches it. [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:42), [`World.kt`](src/commonMain/kotlin/terra/world/World.kt:89)
- No verified count of depressions, flats, inland basins, or ocean outlets exists in code or was computed during this read-only investigation. With arbitrary neighboring noise values and clamping, each is possible, but their prevalence should not be asserted without analysis.
- Weather's horizontal wrap does not imply hydrological world wrap: the world and map are bounded, and the elevation noise is not made periodic. A drainage edge from the last column to the first would therefore introduce a seam unless world generation/topology is deliberately reconciled. Vertical edges should terminate, connect to an outlet, or be treated as polar boundaries by an explicit rule; weather clamping is not an appropriate hydrology rule by default.
- The code has no prescribed neighbor set, so cardinal-only versus 8-neighbor (diagonal) routing is an open choice. Equal-height neighbors can make a naive downhill selection ambiguous; allowing equal-height routing without visited/order rules risks cycles. Independent local steepest descent can also strand cells in sinks.

### Assessment: routing pre-processing

A simple “send flow to the lowest strictly lower neighbor” map is insufficient as a general guarantee of drainage to ocean or another valid sink: a local depression has no lower neighbor; a flat can have no strict descent; an inland basin can be closed; and choosing among equal neighbors can form cycles if equal-height edges are allowed. A lightweight priority-flood or equivalent depression/spillway preprocessing is a plausible way to assign a monotonic drainage order and route interior basins toward outlets, while preserving basin fills as lakes if desired. An alternative is explicit depression detection with lake sinks and calculated spill elevations. Neither exists today and neither should be assumed necessary until the intended lake behavior and map topology are chosen.

Additional risks from the model: FBM detail and clamping may make small-scale drainage noisy; eight-neighbor diagonal routing can create visually diagonal stair-step channels; routing terrain across arbitrary screen/map edges can look discontinuous; river paths over mountain-classified tiles may be physically valid headwaters, but paths must still follow elevation; and using normalized elevation as though it were meters would imply ungrounded slope/flow speeds. Network topology and river discharge should be separated from map artwork and visual biome labels.

## 9. Missing information, ambiguities, and confirmed limitations

- **Confirmed absent:** current river/lake/flood/wetland simulation and assets; soil infiltration parameters; runoff output; groundwater; snowpack/melt; erosion; basin labels; water-level storage; discharge units; river visual connectivity; lake outlets; hydrology-specific scheduling.
- `drainedMm` has no public accessor and is scoped to one local substep. `rainMmThisUpdate` is public but aggregates total precipitation for the outer `step` call and does not distinguish rain absorbed, drainage, overflow, or ocean rain.
- The requested “long-term rainfall” exists only as an exponentially smoothed rainfall rate with 30-day response. The name `thirtyDayRainMmPerHour` could be read as a rolling average, but code implements an EMA. Annual precipitation is annualized from it.
- The project does not define a physical scale for a tile, so converting mm depth to volumetric flow or visual river width requires a new scale assumption. The current elevation is unitless and no slope-to-velocity relation exists.
- Edge topology is inconsistent across systems: weather uses periodic X and clamped Y, world lookup and rendering use bounded coordinates. World noise itself is not periodic at the X seam.
- Terrain is immutable between regenerations; dynamic river levels and floods cannot currently update `Cell.terrain` or any other per-cell state. The renderer can refresh tile map data on world replacement but does not monitor cell mutations.
- Initial soil water is 125 mm for each land tile, so the soil store begins with water independent of weather precipitation history. Ocean evaporation is an unlimited source; this is an intentional simplified model, not a closed global budget.
- It remains a product/design ambiguity whether soil drainage should feed groundwater, direct runoff, or both; whether over-capacity rain should become immediate surface runoff; whether lakes are permanent geometry or dynamic storage; and whether map-edge outlets or a periodic globe should be supported.

## 10. Suggested implementation boundaries

These are preliminary architectural boundaries only; they are not an implementation plan.

1. Keep static geography/routing separate from visual terrain classification. Routing should use elevation and explicit outlet/basin semantics, not the terrain enum alone.
2. Define water accounting first: expose actual per-tile drainage and any soil-capacity overflow, with clear units and aggregation interval. Treat precipitation, drainage, evaporation, and initial soil water as distinct quantities so inputs cannot be counted twice.
3. Build a static acyclic drainage order or explicit basin/spill graph once when the world is generated. Preserve closed basins as lake-capable sinks or provide a documented spill outlet; do not assume local descent always succeeds.
4. Store dynamic river/lake state as millimeter-depth, volume, or discharge values with explicit conversions. Current weather values are depths, and the map has no physical tile area.
5. Advance hydrology from accumulated simulated time at a cadence chosen independently of render frames and overlay refreshes. Keep work bounded per call when users select accelerated simulation speeds.
6. Render water as a procedural connected overlay initially; add authored reusable channel/surface assets only if the desired visual treatment requires them. Keep water draw order above base terrain and below selection/UI.
